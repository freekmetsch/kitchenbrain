What actually went wrong

  • 1False capability. The assistant promised adjustable alternatives, but the contract held one fixed value and one checkbox.
  • 2Retry leakage. Oversized searches, guessed fields, evidence failures, and “let me retry” narration became household-facing chat.
  • 3Duplicate decision surfaces. The final response restated the card, while an older proposal stayed active-looking.
  • 4Stacked width caps. The page rail, bubble cap, and nested card padding discarded most useful horizontal space.

The intended choice

Three options are different by product form and use—not merely brand, price, or package size.

Option 1Whole blockGrate it yourself; recipe-only preference.
Option 2Fresh pre-gratedConvenient, softer texture.
Option 3Grated powderShelf-stable, different cooking result.

No default selection. The agent does not know the preference until the user chooses. “Show 3 more” reveals already staged products; “Find different options” starts a visible, bounded replacement turn.

  • AAH product IDs stay server-side. Browser Apply sends only a server-minted candidate ID.
  • BThe recipe preference lives in an additive table keyed by recipe ID and stable ingredient ID—not in the Dutch name.
  • CMixed preferred, neutral, manual, or conflicting shopping sources block push until explicitly resolved.
  • DA replacement retires the old proposal only after three novel candidates validate; failure preserves the old card and selections.

Five execution phases

  1. Lock the failure into tests

    Seed realistic chat/proposal JSON and make the 24.8-second browser loop fail behaviorally.

  2. Establish proposal and data boundaries

    Opaque evidence, typed choice groups, single-use tokens, additive preference migration.

  3. Carry choices into shopping

    Strict all-source agreement, explicit unresolved rows, stale-product recovery.

  4. Replace the tall chat surface

    Three-column wide choices, compact phone disclosure, wider bubbles, aggregated activity, final-only prose.

  5. Rehearse and promote

    Fresh/upgraded isolated database proof, full gate, deployment-lineage dependency, exact Railway main revision, optional live model canary.
